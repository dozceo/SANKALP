# Smart Revision Planner UX Flow Integrity Report (Task 15)

## Overview
This report validates the integrity of the user flow from ML prediction → ADK decision → LLM explanation → UI rendering. The goal is to identify broken states, missing error handling, and logical gaps that could lead to confusing or incomplete user experiences.

## Flow Analysis

### 1. Partial Failure Handling (Critical)
**Issue:** "All-or-Nothing" Failure Mode
**Location:** `src/ai/flows/smart-revision-planner.ts`
**Description:** The revision planner flow relies on a sequential execution: ML -> ADK -> LLM. If the final step (LLM explanation generation) fails, the entire function throws an error (or returns null via the action wrapper), discarding the perfectly valid revision topics generated by the ADK.
**Impact:** Users receive *no* revision plan simply because the explanation service failed, even though the system knows *what* they should revise.
**Recommendation:** Wrap the LLM call in a `try/catch` block. If it fails, fallback to default static reasons (e.g., "Recommended for revision") and return the list.

### 2. Fallback Logic Transparency (Medium)
**Issue:** Misleading Explanations for Fallback Topics
**Location:** `src/ai/flows/smart-revision-planner.ts` (`makeRevisionDecisions`)
**Description:** When ML prediction fails, the system falls back to including topics based solely on `days_since_last_revision > 10`. It assigns a placeholder `masteryProbability` of `0.5`.
**Flow Gap:** The LLM prompt receives `mastery: 50%` without knowing this is a placeholder. It attempts to explain *why* mastery is 50% (e.g., "You're halfway there!"), which is a hallucination. The true reason is "We haven't seen you practice this in a while."
**Impact:** Users get specific feedback on a metric (mastery) that is actually unknown/mocked.
**Recommendation:** Flag fallback topics in the data structure passed to the LLM (e.g., `isFallback: true`) or skip the LLM explanation for these topics entirely.

### 3. Error Recovery in UI (Low)
**Issue:** Generic Error Message
**Location:** `src/components/planner/ScheduleView.tsx`
**Description:** The UI displays a generic "An Error Occurred" card if the plan generation returns null.
**Impact:** The user doesn't know if they should try again later (server error) or if they need to do something else (data error).
**Recommendation:** Implement more granular error states. If the error is due to "No topics found" vs "AI Service unavailable", the UI should guide the user differently.

## Conclusion
The core revision logic is robust, but the dependency on the LLM for explanations introduces a fragility to the entire feature. Decoupling the "what" (ADK) from the "why" (LLM) with proper error boundaries is essential for reliability.
