# Mock Data Consistency Report

## Executive Summary
This report analyzes the structural consistency of mock data generation and storage mechanisms within the Student Intelligence Platform, specifically comparing the loose JSON storage of `src/lib/mock-db.ts` and the synthetic data generation in `src/ml/training/generate_data.py` against the strict TypeScript interfaces defined in `src/data/docsData.ts` and `src/types/intelligence.ts`.

## Scope
- **Components Audited**:
    - `src/lib/mock-db.ts`: In-memory Firestore mock with file persistence.
    - `src/ml/training/generate_data.py`: Synthetic data generator for ML training.
    - `src/data/docsData.ts`: Defines `StudentNode`, `Subject`, `Badge` types.
    - `src/types/intelligence.ts`: Defines `MasterySignal`, `StudentRiskProfile`.

## Findings

### 1. Inconsistent Schema Enforcement
- **Issue**: `src/lib/mock-db.ts` uses `any` for `data` property and lacks any runtime validation (e.g., Zod schemas) when reading/writing from `mock-db.json`.
- **Evidence**: `this.data: Record<string, any> = {};` allows storing arbitrary structures that may violate `StudentNode` or `Quiz` interfaces.
- **Impact**: UI components relying on specific fields (e.g., `student.masteryScores`) may crash if mock data is malformed or missing required properties.

### 2. ML Training Data Schema Mismatch
- **Issue**: The synthetic data generated by `generate_data.py` uses snake_case column names (`avg_quiz_score`, `attempts_per_topic`) while the frontend interfaces in `intelligence.ts` use camelCase (`score`, `attempts`).
- **Evidence**:
    - `generate_data.py`: `'avg_quiz_score': ...`, `'days_since_last_revision': ...`
    - `intelligence.ts`: `score: number;`, `daysSinceRevision: number;`
- **Impact**: Direct usage of ML model outputs without a transformation layer will fail. The `ml-bridge.ts` must handle this mapping explicitly, which introduces a maintenance burden and potential for errors.

### 3. Missing Quiz Data Validation
- **Issue**: `mock_quiz_generations.json` (if used) is not validated against a `Quiz` schema.
- **Evidence**: No `Quiz` interface validation found in `mock-db.ts` or `src/ai/flows/adaptive-quiz-engine.ts` during load.
- **Impact**: Inconsistent quiz data (e.g., missing `correctAnswer`) could lead to runtime errors in the Quiz UI.

## Recommendations

### Short Term
1.  **Add Zod Validation**: Introduce Zod schemas for key entities (`StudentNode`, `Quiz`) and validate data on load in `mock-db.ts`. Log warnings for invalid entries.
2.  **Explicit Mapping Layer**: Create a dedicated `MapMLToFrontend` utility function in `src/ml/inference/ml-bridge.ts` to strictly type and convert snake_case ML outputs to camelCase frontend objects.

### Long Term
1.  **Shared Schema Definition**: Define schemas in a language-agnostic format (e.g., JSON Schema or Protocol Buffers) and generate both TypeScript interfaces and Python data classes/validators from a single source of truth.
2.  **Schema Migration Testing**: Implement tests that verify old mock data files can still be read by the new schema, or provide migration scripts.

## Conclusion
The current mock data infrastructure is flexible but fragile. Implementing strict schema validation at the boundaries (Database Load, ML Inference) is essential to prevent "silent failures" where data inconsistencies cause UI bugs or logic errors.
